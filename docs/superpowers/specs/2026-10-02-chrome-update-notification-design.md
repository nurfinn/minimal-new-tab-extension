# Уведомление о готовом обновлении — Chrome

Дата: 2 октября 2026 года. Статус: UX согласован в чате; эта письменная спецификация ожидает проверки пользователя. Реализация ещё не начата.

## 1. Задача и границы

Пользователь хочет заметить уже готовое обновление Minimal Tab и применить его в удобный момент, не потеряв данные в открытых вкладках. Сейчас работаем только над Chrome. Перенос накопленных изменений в Firefox — отдельный следующий этап.

Утверждённый сценарий: компактный баннер внизу слева, «Обновление готово» / “Update ready”, действия «Обновить» / “Update” и «Позже» / “Later”. «Позже» скрывает сообщение на 24 часа. Применение — только по нажатию и после проверки всех страниц расширения.

Это не исправление доказанной причины отставания старых магазинных установок: такая причина не установлена. Механизм начнёт помогать после установки версии, которая его содержит; код не может изменить уже установленную 1.5.4 задним числом.

Вне scope: сервер версий, OAuth, аналитика, опрос магазина, новые разрешения, системные уведомления, принудительное автообновление, новые настройки, переписывание storage, миграция данных, новый фон, версия релиза, установка в личные браузеры, push и публикация.

## 2. Интерфейс

- Небольшой баннер внизу слева, в текущей визуальной системе. Шапка и основные кнопки не смещаются. Баннер не перекрывает нижний ряд карточек в крайнем положении прокрутки; учитываются безопасные отступы и узкое окно.
- Не открывает модальное окно, не звучит, не перехватывает фокус. Текст объявляется через спокойный `role="status"`; действия доступны с клавиатуры и имеют видимый фокус.
- Над открытой модальной формой баннер не показывается и не принимает ввод. После закрытия формы появляется, если обновление всё ещё актуально и не отложено.
- «Позже» скрывает баннер во всех вкладках этого профиля на 24 часа для этой пары текущей и целевой версий. Новая целевая версия не наследует отсрочку старой. После истечения срока баннер возвращается при открытии/активации вкладки; отдельного таймера показа поверх текущей работы нет.
- Откладывание касается только сообщения. Оно не удерживает расширение активным и не мешает штатному применению обновления Chrome.
- При нажатии «Обновить» повторные клики кратковременно блокируются. Если применение небезопасно, остаётся баннер с пояснением: «Завершите редактирование и дождитесь сохранения во всех вкладках Minimal Tab» / “Finish editing and wait for saving in all Minimal Tab tabs.” Автоматического применения после исчезновения причины нет: пользователь нажимает ещё раз.
- Если проверить безопасность невозможно: «Не удалось проверить открытые вкладки. Обновление не применено» / “Could not check open tabs. The update was not applied.” Не показывать ложное сообщение об успехе.
- Все состояния имеют русский и английский текст. Политика текущей локализации сохраняется.

## 3. Источник сигнала и небольшие служебные данные

Единственный источник нового предложения — `chrome.runtime.onUpdateAvailable` с корректной версией, которая строго новее текущего manifest. Сравнение числовое по компонентам, не лексикографическое. Повтор одного события не создаёт повторный баннер и не сбрасывает отсрочку; старые и повреждённые версии игнорируются.

Обработчик регистрируется при запуске Chrome-страницы до ожидания загрузки пользовательских данных. При отсутствии страниц расширения оставляем штатный механизм Chrome; фонового процесса, keep-alive, `requestUpdateCheck`, сетевых запросов и обхода правил браузера не добавляем.

Отдельные имена ключей, не часть application state:

- `chrome.storage.session`: текущая подтверждённая пара `baseVersion` / `targetVersion`, полученная от события Chrome. Новая вкладка в той же сессии может восстановить уведомление из неё. Версии валидируются; данные от другого `baseVersion` не используются. Недоступность session API допускает работу только с достоверным событием в живых страницах, без выдуманного pending update.
- `chrome.storage.local`: пара версий и `snoozedUntil` для отсрочки на 24 часа между запусками браузера. Этот ключ сам по себе никогда не означает наличие обновления. При записи срок равен текущему времени плюс 24 часа; при чтении принимается только конечное число между текущим временем и текущим временем плюс 24 часа. Остальное не скрывает сообщение, в том числе при повреждённых данных или существенном переводе часов назад.

Ошибки служебного чтения/записи не ломают интерфейс. Если отсрочку не удалось записать, баннер скрывается в живых вкладках через их общий координационный интерфейс, но 24-часовая отсрочка после закрытия этих страниц не гарантируется. Ошибка не должна порождать перезапуск или запись fallback в пользовательское хранилище. Не писать при рендере, свайпе или каждом открытии вкладки; только при новом событии/явном откладывании и очистке устаревших собственных ключей. В sync ничего не добавляется.

## 4. Безопасное применение в нескольких вкладках

Проверяются только страницы самого расширения через `chrome.extension.getViews()`, без доступа к истории и сторонним вкладкам. Страница предоставляет узкий внутренний интерфейс готовности и краткой блокировки действий, а не сайты, URL, формы или всё состояние приложения.

Причины отказа: незавершённая инициализация; открытый диалог (даже пока не изменённый); редактирование/переименование; перетаскивание; чтение/обработка файла; импорт; незавершённая операция сохранения; отложенное сохранение выбранной папки. Неизвестная или недоступная страница, устаревший интерфейс, исключение и неполный ответ также означают отказ, а не разрешение.

Для выбранной папки учитывается и `pendingFolderSelection`, и выполняющаяся запись. Успех нельзя выводить только из завершения Promise: текущий путь сохранения может вернуть управление после ошибки, оставив pending-состояние. Изменять политику повторной записи или storage-схему в этом этапе не нужно.

Порядок применения:

1. Проверить, что есть достоверное предложение обновления и API доступен.
2. Получить все страницы расширения. У каждой запросить готовность и краткую блокировку новых пользовательских изменений. Двойное применение из другой вкладки отклоняется.
3. При любом отказе освободить уже взятые блокировки и объяснить причину. Не закрывать формы, не сохранять их за пользователя, не терять фокус или содержимое.
4. Повторно проверить набор страниц и их готовность. Новая/исчезнувшая/неинициализированная страница или новая операция отменяют попытку. Новая страница не начинает изменения, пока идёт подготовка применения.
5. Сразу после финальной проверки, без асинхронного промежутка, вызвать `chrome.runtime.reload()` один раз. Именно расширение, не весь браузер. Если проверку в реальных контекстах нельзя надёжно выполнить, вызов запрещён.
6. При исключении до успешной отправки команды освободить блокировки и показать ошибку. Если команда отправлена, но за 3 секунды переход не наблюдается, показать объяснение и инструкцию переоткрыть вкладки Minimal Tab. Таймаут не доказывает отмену команды: не разрешать новые изменения поверх потенциально отложенного перезапуска. Восстановление в этом редком случае — переоткрытие страниц без обхода защиты; не оставлять без объяснения зависшую кнопку и не показывать «успешно» лишь по возврату из `reload()`.

Это координация страниц расширения, а не управление обновлятором браузера. Она не отменяет независимые штатные обновления Chrome. Безопасность общего перезапуска и поведение при появлении/закрытии страниц — обязательная браузерная проверка, не допущение из одного unit-теста.

## 5. Разделение кода и Chrome / Firefox

- `chrome-update-service.mjs`: версии, события, отсрочка, работа только с собственными служебными ключами, координация применения. API подставляется в тестах; сервис не читает DOM приложения и пользовательский state.
- `chrome-bootstrap.mjs` и `chrome-update.css`: подключение сервиса, небольшой баннер и локализованные сообщения. Подключаются только Chrome builder; обычное превью без API безопасно не показывает баннер.
- `newtab.js`: минимальный нейтральный интерфейс готовности/блокировки и учёт незавершённых операций. Существующие пути сохранения, формы, emoji и свайпы не переписываются. Сам по себе этот интерфейс не слушает события обновлений и не перезапускает расширение.
- `scripts/build-chrome.mjs`: включает новые файлы и заменяет точку запуска в своей копии HTML. Общий исходный `newtab.html` и Firefox entry point не переключаются на Chrome bootstrap.
- Локализация использует существующие RU/EN ресурсы и английский fallback. Изменения общих файлов отражаются в проверяемом baseline; это не перенос функциональности обновления в Firefox.
- Firefox-специфические manifest, bootstrap и обработчики обновлений не меняются. Firefox-сборка не должна содержать Chrome bootstrap/service или регистрировать `onUpdateAvailable`. Обе магазинные ZIP и личные установки остаются нетронутыми.

Если реальная проверка покажет, что без фонового компонента нельзя обеспечить выбранный сценарий, не добавлять его молча: остановить реализацию этого пути, записать ограничение и согласовать изменение архитектуры.

## 6. Проверки и критерии приёмки

Unit/contract: корректные и повреждённые версии; повтор/порядок событий; восстановление подтверждённой пары; отсрочка на 24 часа и новая версия; недоступные API; ошибки чтения/записи; отсутствие sync-записей и опроса магазина; неизвестная страница; любой busy-флаг; ошибки и no-op reload; повторные клики; освобождение всех блокировок при отказе до команды и понятное безопасное восстановление при неизвестном результате после неё. Полный существующий тестовый набор должен оставаться зелёным.

Браузер, изолированный Chrome: RU/EN и узкое окно, фокус и клавиатура, скролл и баннер; два окна с несколькими вкладками; форма/файл/импорт/drag в соседней вкладке; медленное и ошибочное сохранение, включая отложенную папку; появление/закрытие страницы во время проверки; одновременные клики; отсутствие застрявших блокировок; сохранность сайтов, папок, emoji, фона и выбранной папки после контролируемого reload.

Сначала проверить доставку события и доступ к guard-интерфейсам настоящих extension pages, в том числе `chrome://newtab/`, а не только localhost. Если в доступной версии Chrome нельзя получить реальный update event без магазинного обновления, явно разделять наблюдаемый API-контракт и синтетическую доставку.

В распакованной QA-сборке сигнал готовности подаётся только тестовым инструментом; в релизном пакете нет кнопки симуляции, URL-параметра или публичного сообщения, способного создать ложное обновление. Реальный `runtime.reload()` проверяется отдельно от имитации установки новой версии. Имитация не доказывает скачивание и применение подписанного пакета Chrome Web Store.

Отдельные build-тесты подтверждают изоляцию Firefox и прежние разрешения. Для этапа достаточно реализованного и проверенного Chrome-сценария с явно указанным ограничением реальной магазинной доставки; релизная приёмка обновления из магазина остаётся отдельной проверкой, не объявляется выполненной.

## 7. Основания и следующий этап

В текущем manifest нет background/service worker, в исходниках нет `onUpdateAvailable`, `requestUpdateCheck` или `runtime.reload`. У приложения уже есть асинхронная инициализация, несколько путей сохранения и отложенная запись выбранной папки — их необходимо учитывать явно.

Официальные источники, сверенные 2 октября 2026 года:

- [Chrome: жизненный цикл обновления](https://developer.chrome.com/docs/extensions/develop/concepts/extensions-update-lifecycle) — открытые страницы могут задерживать применение; событие готовности относится к скачанному обновлению; ограничения собственных проверок.
- [Chrome runtime](https://developer.chrome.com/docs/extensions/reference/api/runtime#event-onUpdateAvailable) — событие, версия и reload.
- [Chrome extension.getViews](https://developer.chrome.com/docs/extensions/reference/api/extension#method-getViews) — окна страниц самого расширения.
- [Chrome storage](https://developer.chrome.com/docs/extensions/reference/api/storage) — отдельные local/session области.

После проверки этой письменной спецификации пользователем — короткий implementation plan с файлами, порядком проверки и выбранным способом выполнения. Этот документ не разрешает незаметно перейти к реализации или обновлению личных установок.
