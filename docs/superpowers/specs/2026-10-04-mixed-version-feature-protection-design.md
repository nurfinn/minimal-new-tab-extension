# Защита emoji и видимости All при работе со старой версией

Дата: 4 октября 2026 года. Статус: спецификация и план подтверждены пользователем; выбор исполнения делегирован «сам решай». Реализация выполнена Native-методом, финальные автоматические проверки проходят; независимое ревью выполняется. [Свежие результаты и ограничения](../../mixed-version-feature-protection-verification-2026-10-04.md). Выпуск и личные установки не входят в этот этап.

## 1. Задача и критерий успеха

Пользователь готовит следующий релиз Minimal Tab для Chrome и Firefox. Нужно устранить воспроизведённую потерю новых настроек, когда опубликованная 1.6 на другой установке сохраняет обычное изменение в общем browser sync-хранилище.

Проверка с настоящими сериализаторами обоих опубликованных ZIP 1.6 показала: переименование сохраняет сайты, папки, порядок, фон и само новое название, но удаляет неизвестные старому коду `emoji` и `showAllFolder: false`. Простое чтение старым клиентом ничего не удаляет. Исходная диагностика и её ограничения зафиксированы в [release acceptance](../../release-acceptance-2026-10-04.md).

Целевой сценарий: новая версия сохраняет emoji и скрывает All; 1.6 несколько раз переименовывает, перемещает или переупорядочивает сайты; новая версия принимает эти изменения, сохраняя emoji и скрытую All. Намеренный возврат к favicon и включение All должны сохраняться так же надёжно — защита не должна «восстанавливать» отменённую настройку.

В scope: протокол хранения этих двух настроек, чтение/запись, переход с текущей тестовой сборки, ошибки, совместимость и проверки в обеих сборках. Интерфейс, разрешения, сетевые сервисы, фон, жесты, каталог emoji и формат JSON не перерабатываются. Допустима только необходимая обработка ошибки через уже существующие механизмы состояния/сообщения. Версия релиза, личные установки, магазинные архивы, push и публикация в этот этап не входят.

## 2. Выбранный подход

Новые настройки получают собственный небольшой слой в `storage.sync`. Основной формат остаётся `storageVersion: 1`, чтобы опубликованная 1.6 продолжала читать и менять сайты и папки. Это не копия всей базы: слой хранит только выбранный emoji или явный возврат к favicon и видимость All.

Рассмотренные альтернативы:

- Локальная резервная копия не защищает настройку на другом устройстве и может возвращать намеренно отменённые emoji.
- Повышение версии основного payload делает его неприемлемым для валидатора 1.6 и рискует вызвать загрузку defaults вместо пользовательских данных.
- Отдельный sync-слой не затрагивается обычным сериализатором и очисткой 1.6; выбран этот подход.

Гарантия ограничена опубликованными Chrome/Firefox 1.6 и их обычными записями. Она не распространяется на произвольный старый код, `storage.clear()`, удаление расширения, сброс профиля или конфликты одновременно изменённых основных данных. Chrome Sync и Firefox Sync — разные системы; новая схема не синхронизирует Chrome с Firefox.

## 3. Данные и независимые имена ключей

Отдельные ключи:

- `minimalNewTabFeatureManifest` — активное и предыдущее поколения нового слоя.
- `minimalNewTabFeatureManifestBackup` — дескриптор последнего исправного поколения до публикации нового.
- `minimalNewTabFeatureChunk:<generationId>:<index>` — части JSON этого слоя.

Ни один ключ не начинается с `minimalNewTabSyncChunk:`. Реальный код 1.6 удаляет только ненужные части с этим старым префиксом; обе опубликованные реализации должны подтвердить сохранность новых ключей тестами.

Feature payload версии 1 содержит `featureVersion: 1`, явный boolean `showAllFolder` и map `sites`. Запись сайта содержит его ID как ключ, `urlHash` и `emoji`. `urlHash` — SHA-256 в lowercase hex от UTF-8 результата существующего `normalizeWebUrl`; полный адрес, включая query и fragment, участвует в идентичности. Нельзя сравнивать только hostname или использовать короткий самодельный hash.

`emoji` — значение, принятое существующим `normalizeSiteEmoji`, или `null`, означающий явный выбор обычной иконки сайта. В map нужны сайты с emoji и ранее защищённые, ещё существующие сайты с явным сбросом. Сайты, у которых никогда не было emoji, не получают пустую запись. Отсутствие записи в исправном полном поколении также означает стандартную иконку, а не поиск emoji в более старом поколении. Boolean `true` для All обязателен: отсутствие поля не заменяет намеренное включение.

В основном payload нового писателя сохраняются совместимые inline-поля emoji/All и добавляется `featureState: { version: 1, generationId }`. Эта отметка означает, что inline-поля — полное намерение нового писателя: отсутствие emoji является выбором favicon, отсутствие `showAllFolder: false` — выбором показывать All. `generationId` ссылается на соответствующее поколение feature-слоя. 1.6 допускает дополнительные поля при чтении, но её следующая сериализация удаляет эту отметку вместе с новыми inline-полями.

Метка нужна для частичного поступления sync-ключей, а не для угадывания версии по времени. Не использовать `createdAt` как глобальный порядок изменений: часы устройств могут различаться. Повторно использовать поколение, если feature-содержимое не изменилось. Канонический JSON сортирует ID независимо от порядка карточек, чтобы reorder не выглядел изменением настроек.

Хеширование не считается анонимизацией. Дополнительных запросов, аналитики или сторонних получателей данных нет; используется существующее браузерное хранилище.

## 4. Правила чтения

Одно чтение `syncArea.get(null)` даёт локальный снимок ключей. Сначала выбирается исправное основное поколение по существующей цепочке main/previous/backup. Ошибка feature-слоя никогда не делает валидные сайты/папки невалидными и не переводит всю базу в defaults.

| Основной снимок | Feature-слой | Результат |
| --- | --- | --- |
| Корректная отметка нового писателя | Исправное поколение с тем же ID | Использовать согласованное поколение; проверить соответствие inline-намерению |
| Корректная отметка нового писателя | Поколение ещё не пришло, повреждено или имеет другой ID | Использовать полный inline-снимок; не применять другой feature-снимок поверх него |
| Без отметки, feature-слой существует | Исправный активный feature-снимок | Основные данные взять из core, новые настройки — из feature-слоя |
| Без отметки, активный feature-снимок не читается | Исправный previous/backup | Использовать целиком это восстановленное поколение; не собирать поля из разных поколений |
| Без отметки, feature-ключи есть, но ни одно поколение не читается | Нет достоверного feature-снимка | Показать валидные основные данные; не уничтожать feature-ключи и не разрешать запись поверх неизвестных настроек |
| Без отметки и без feature-ключей | Обычная опубликованная 1.6 | Загрузить как прежде, без записи и миграции пустых настроек |

Для доверия полному inline-намерению нужны поддерживаемая версия отметки, допустимый generation ID и корректные необязательные inline-поля: присутствующий emoji должен проходить нормализатор, присутствующий `showAllFolder` должен быть boolean. Повреждённая отметка не превращает новый снимок в «старый без отметки». Если inline-поля повреждены, но достоверно читается именно указанное feature-поколение, настройки берутся из него; иначе основные данные доступны, но запись поверх неизвестного намерения запрещена. Неизвестная будущая версия feature-протокола также не считается отсутствием слоя и не перезаписывается. При корректном inline-намерении несогласованный feature-снимок этого же ID считается повреждённым, а inline остаётся fallback.

При overlay применять emoji только к существующему сайту с совпавшими ID и `urlHash`. Не создавать сайты, не менять URL, названия, folderId или порядок из metadata. Основной снимок всегда является источником существования сайтов и папок.

Feature-настройки объединяются с payload до материализации выбранной папки и обычной нормализации навигации. Иначе выбранный `root` ошибочно превратится в All, хотя All скрыта. Существующие правила остаются: без пользовательских папок All доступна; при скрытой All сайты без папки доступны через root; недоступный выбор заменяется первой видимой папкой.

Обычное чтение существующего исправного слоя не пишет ничего в sync. При неполной удалённой доставке следующий обычный reload/read повторно разрешает снимок; не добавлять polling или записи «на исправление» при каждом рендере.

## 5. Намеренные изменения, импорт и идентичность

- Выбор emoji записывает нормализованное значение. «Использовать иконку сайта» заменяет ранее защищённое значение на `null`. После записи 1.6 обе ситуации восстанавливаются из актуального слоя, не из истории.
- Включение/скрытие All сохраняет явный boolean. Принудительная доступность All после удаления последней пользовательской папки остаётся текущим продуктовым поведением, а не новой скрытой настройкой.
- Переименование, перенос в другую папку и reorder не меняют идентичность сайта и его emoji. Изменённый старым клиентом URL с прежним ID не получает emoji прежнего адреса. В новой форме смена URL связывает новый адрес с актуальным выбором иконки из этой формы.
- Удалённый сайт отсутствует в core и не восстанавливается из feature-слоя. При следующем успешном изменении новой версией его запись удаляется из нового feature-поколения. Чтение само по себе не выполняет очистку.
- Импорт через новую версию — явная замена сайтов: v2 применяет перечисленные emoji; v1 или отсутствие emoji означает favicon даже при совпадении прежнего ID и URL. Видимость All остаётся текущей настройкой браузера назначения, как в текущем импорте. Feature-метаданные не добавляются в JSON-файл.
- Старый импорт, который воспроизводит ровно тот же ID и URL, неотличим от обычной записи старого клиента. В этом случае сохраняется последнее защищённое значение. Это принципиальное ограничение: 1.6 не передаёт намерение сбросить emoji. Не обещать распознавание такого сброса или идентичного повторного создания задним числом.

Записи `null` сохраняются только для существующих ранее защищённых сайтов; бессрочный журнал удалений не нужен. Уже потерянные до появления защиты emoji нельзя достоверно восстановить без реального backup — не назначать значки автоматически по доменам.

## 6. Первый запуск и переход с текущей тестовой сборки

Опубликованная 1.6 без новых настроек загружается без перезаписи сайтов, папок, выбора, фона или добавления feature-ключей.

Если feature-ключей ещё нет, но текущий валидный unmarked payload содержит emoji или скрытую All, это ранее сохранённое состояние тестовой сборки. Первый запуск новой версии однократно создаёт feature-слой из этих inline-настроек, не переписывая core. Создание выполняется под существующей очередью/блокировкой с повторным чтением: нельзя публиковать устаревший bootstrap из другой вкладки. После успешного bootstrap уже обычная запись 1.6 не уничтожает защищённые значения.

Если bootstrap не удалось сохранить, исходный inline-снимок остаётся читаемым, ключи core не меняются, успех защиты не объявляется. Сервис сообщает ошибку существующим путём; запись нового пользовательского изменения требует сначала завершить защиту или завершается с ошибкой. Повторный запуск/попытка может повторить bootstrap, без busy-loop. Когда слой уже существует, unmarked writer обрабатывается по таблице чтения, а не повторно мигрируется.

Отсутствие нового слоя на устройстве до его доставки браузером не даёт возможности восстановить стёртое новым для этого устройства поле. Гарантия начинается после успешной публикации и наличия валидных feature-данных; она не ускоряет cloud sync.

## 7. Запись, публикация и отказ

`createStorageService` остаётся владельцем I/O, очереди и `minimal-new-tab-state` lock. Публичные методы `load`, `save`, `update` и их привычные результаты сохраняются. `update` читает свежий объединённый снимок перед transform; ошибка чтения защиты не разрешает сохранить defaults поверх неё. Прямой `save` остаётся записью переданного полного намерения, а не merge произвольного stale-снимка из другого устройства.

Сравнение no-op выполняется по эффективному пользовательскому состоянию без служебной отметки, а не только по raw legacy JSON. Повторное сохранение неизменного прочитанного состояния не переписывает core ради добавления отметки. При первой реальной записи без feature-слоя он создаётся даже для пустой map и `showAllFolder: true`, чтобы опубликованный marked core имел соответствующее защищённое поколение. Отдельный bootstrap существующих недефолтных настроек остаётся исключением раздела 6.

Для одной операции:

1. Валидировать core и feature-кандидаты, определить изменение канонического feature JSON. Сначала проверить доступность нужной защиты и ограничения размера.
2. Подготовить части новых поколений; если feature-содержимое не изменилось, не создавать и не записывать его заново. Записать подготовленные chunk-ключи до публикации дескрипторов.
3. Сохранить дескрипторы предыдущих исправных поколений в backup. Не стирать предыдущие данные заранее ради свободного места.
4. Опубликовать основной manifest и, при изменении слоя, feature manifest одним локальным `StorageArea.set` с несколькими ключами. Core содержит согласованную отметку. Это локальная точка публикации, а не обещание распределённой транзакции браузерного аккаунта.
5. Проверить локальным чтением, что опубликованные дескрипторы и данные доступны и соответствуют намерению. Только тогда возвращать успешное сохранение защищённой настройки и обновлять собственные last-valid caches.
6. После подтверждения выполнить ограниченную очистку собственных ненужных поколений. Её ошибка — предупреждение, не отмена уже сохранённых пользовательских данных.

При известной ошибке до публикации исправные manifests и их данные остаются предыдущими. Нет «успешно, но только в local» или молчаливого отбрасывания emoji ради quota. Ошибка квоты/записи возвращается существующим error-путём; форма и её несохранённый выбор остаются доступны.

При отказе/прерывании на публикации результат может быть неопределённым: повторно прочитать хранилище, сохранить доступные валидные поколения и не объявлять успех без проверки. Не откатывать целые manifests автоматически — это способно затереть чужую более новую запись. Если чтение тоже невозможно, сообщить неуспех, сохранить резервные данные и не удалять подготовленные части. Частичная/неподтверждённая операция не получает гарантию успешной защиты. Отдельно проверить этот сценарий, а не считать rejected Promise доказательством полного rollback.

При передаче удалённых ключей отдельно или в разном порядке правила раздела 4 не позволяют старому feature-снимку отменить намеренный reset в новом core. Валидный unmarked core от 1.6 совмещается с отдельным подтверждённым feature-слоем. Concurrent remote writes основных данных остаются под политикой самого браузера; lock координирует вкладки этого профиля, не устройства и не две разные системы sync.

## 8. Квоты, валидация и очистка

Для sync актуальные общие ограничения: 102 400 bytes, 8 192 bytes на item и 512 items. Chrome также ограничивает частоту записей: 120 операций в минуту и 1 800 в час. [Chrome storage API](https://developer.chrome.com/docs/extensions/reference/api/storage), [Mozilla storage.sync](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/sync).

Поэтому после первоначального создания feature-поколение не обновляется при свайпе, рендере, reorder или core-only save с неизменными новыми настройками. Ключи и JSON-экранирование учитываются в per-item размере; длина JS-строки не равна размеру хранения.

Feature JSON ограничен 32 768 UTF-8 bytes, chunk — 3 500 UTF-8 bytes, поколение — не более 10 chunks. Этот предел не повышает допустимое число сайтов и не гарантирует, что максимально допустимая база всегда помещается вместе с резервными копиями в общую квоту. Проверки используют общий расход core + feature + остальные sync-ключи, включая временный пик записи, а не только размер нового слоя. При нехватке места — безопасный отказ, не предварительное удаление единственной исправной копии.

Дескрипторы проверяют версию, generation ID, точное соответствие собственного префикса и индексов, количество chunks, byteLength и допустимые пределы до сборки JSON. Emoji, boolean и hex-идентичность проверяются отдельно; keys не должны позволять prototype pollution. Некорректная необязательная запись emoji не должна уничтожать core-данные; применять fallback только целыми достоверными feature-поколениями. Недоступность или ошибка SHA-256 означает отказ нужной операции, не переход на слабый hash или сравнение только домена.

Хранить активное и одно предыдущее исправное feature-поколение; backup ссылается на предыдущее, не создаёт бесконечную историю. Более старый корректный marked core всё ещё содержит inline-намерение и не нуждается в бесконечном удержании feature-chunks.

Очистка feature-слоя читает актуальные собственные manifests и удаляет только доказанно неиспользуемые части собственного завершённого/заброшенного поколения. Не сканировать чужие префиксы и не удалять любые неизвестные feature-chunks другой операции. После неопределённого исхода запись/очистка требует нового достоверного чтения. Пределы основного протокола, его существующая политика recovery и локальное хранение изображений не переписываются этим этапом.

## 9. Границы кода

- Новый `feature-state.mjs`: чистая схема, валидация, канонизация, построение записей/сбросов, SHA-256 identity и применение настроек к существующему core. Не содержит DOM, browser I/O, таймеров или новых сетевых зависимостей.
- `storage-service.mjs`: чтение согласованных поколений, bootstrap, подготовка и публикация обоих слоёв, error/no-op и ограниченная очистка. Не разносить browser I/O по обработчикам формы.
- `newtab.js` / `newtab-core.mjs`: только необходимая проверка правильного порядка merge/навигации и сохранения намерения при reset/import. Визуальная форма, drag, свайпы и их тайминги не переделываются.
- Оба build allowlist и packaging tests включают новый runtime helper; Firefox baseline обновляется только для действительно изменённых общих файлов. Разрешения и Firefox consent остаются прежними.
- Диагностика continuity перестаёт ожидать потерю новых полей и проверяет сохранность с реальными исходниками опубликованных пакетов. Старые диагностические отчёты сохраняются как историческое доказательство причины.

Не выделять общий новый storage framework и не выполнять широкую реорганизацию существующего сервиса. При необходимости локальная обработка feature-generation отделяется, чтобы публикацию/валидацию можно было тестировать независимо.

## 10. Приёмка и доказательства

Регрессионные тесты сначала должны воспроизвести проблему на текущем коде. Далее обязательны:

1. Настоящие Chrome/Firefox writer 1.6: чтение без записи; несколько последовательных rename/move/reorder/save; сохранность новых ключей после старой cleanup; принятие самих legacy-изменений и сохранность выбранных emoji/скрытой All.
2. Выбрать emoji → сохранить → вернуть favicon → сохранить → старая запись → favicon остаётся. Скрыть All → показать → старая запись → All остаётся видимой. Сброс всех emoji тоже явное намерение, не отсутствие защиты.
3. URL-изменение с тем же ID; переименование/перенос без смены URL; удаление; ID с другим URL; новый импорт v1/v2, включая совпавшие ID/URL и отсутствие emoji; последняя папка, root и восстановление выбранной папки. Старый идентичный импорт отдельно подтверждает заявленное ограничение.
4. Переход со старой 1.6 без записей; однократный bootstrap существующих inline-emoji/All; несколько вкладок; отказ bootstrap без изменения core; no-op и отсутствие лишних feature-записей при core-only изменениях.
5. Core-first и feature-first доставка, отсутствующие chunks, stale generation, несовпадение inline, повреждённая/неизвестная версия, правильная previous/backup цепочка. Ни один вариант не заменяет валидные сайты/папки defaults и не превращает повреждённый слой в явно сброшенный.
6. Ошибка каждого этапа set/get/remove, частично применённый/неопределённый commit, квота и перезапуск между этапами; отсутствие ложного успеха, сохранность last-valid данных и отсутствие опасной cleanup/rollback. Межустройственная атомарность не является ожидаемым результатом теста.
7. Размеры длинных ID, emoji-составных последовательностей, 10 chunks, пик общего расхода и сохранение доступной исправной копии. Граница записи не зависит от числа emoji в каталоге.

После service-проверок: полный unit/contract набор, обе сборки, UI/emoji/жесты/backup regression, Firefox lint, RU/EN и узкое окно. В изолированном Chromium проверить настоящие extension/storage API, обновление тем же ID/путём, reload и закрытие/повторный запуск с сохранёнными emoji/All. Firefox engine/model проверки не выдавать за signed-install или настоящий account sync; нативная проверка временного дополнения возможна отдельно, без личного профиля.

Проверяемые runtime-папки и ZIP должны соответствовать друг другу байт-в-байт. Опубликованные 1.6 ZIP, текущие личные установки и утверждённые обои/иконки неизменны. Отчёт разделяет автоматические проверки, реальную изолированную установку и неисполненные проверки account/store delivery. Только после зелёной регрессии можно убрать соответствующий release risk из README и новой приёмки; исходный исторический отчёт не переписывается как «проблемы никогда не было».

## 11. Ограничения и источники

Защита сохраняет успешно опубликованные настройки при обычной записи известного старого сериализатора. Она не разрешает общий конфликт одновременных редактирований сайтов, не гарантирует порядок cloud delivery и не восстанавливает данные, которых нет ни в одном достоверном снимке. Сохранение локальными API не доказывает доставку аккаунтом. Полная очистка sync удалит оба слоя.

Официальные источники сверены 4 октября 2026 года:

- [Chrome storage API](https://developer.chrome.com/docs/extensions/reference/api/storage): async API, sync-квоты и ограничения записи.
- [Mozilla storage.sync](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/sync): квоты и разрешение конфликтов отдельных ключей браузером.
- [Mozilla StorageArea.set](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/StorageArea/set): запись нескольких ключей и success/rejection Promise; не основание обещать распределённую транзакцию.

Проверка написанной спецификации пользователем — отдельный этап workflow brainstorming. После её подтверждения составляется implementation plan с конкретными файлами и порядком тестов. В этом документе нет подтверждения выполненного исправления или готового релизного архива.
