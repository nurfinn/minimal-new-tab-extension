# Minimal New Tab — общий план следующего релиза

Дата: 22 сентября 2026 года.

Статус на 2 октября: emoji, быстрые свайпы, согласованная UI-полировка и Chrome-only уведомление о готовом обновлении реализованы. Проверенное состояние зафиксировано локальным коммитом `5c98ba1` в рабочей ветке, без push и слияния в main. Нативные проверки Firefox пройдены в указанном ниже объёме. После этого добавлена отдельная проверка сохранности данных и переноса JSON. Полная релизная приёмка не завершена; номер следующего релиза пока не назначен. Старые этапы ниже — история, а не перечень того, что нужно реализовать заново.

## Актуальный порядок — 2 октября 2026 года

1. **Сохранность данных и визуальная проверка (2–3 октября):** пройдены 247 unit/contract и 13 continuity checks; сохранность данных и JSON-перенос описаны [отдельно](../../data-continuity-verification-2026-10-02.md). Свежие 40 Settings browser checks RU/EN проходят. Пустые карточки нативного Firefox воспроизводятся на автоматических снимках свёрнутого окна; после восстановления того же окна появляются без reload/reimport. В шести повторных импортах видимого окна все 13 карточек выбранной папки отрисованы на всех 18 кадрах. Продуктовый код и blur не менялись. Точное состояние окна прежнего запуска не зафиксировано; будущие скриншоты делать с восстановленным окном. [Визуальные доказательства и ограничения](../../visual-acceptance-2026-10-03.md).
2. **Открытые приёмочные пункты:** настоящая cross-device sync, полный перезапуск с подписанным новым Firefox-дополнением, доставка подписанного обновления из магазинов. Не подменять их проверкой reload, ручным копированием sync или повторной временной установкой. Причина отставания старых магазинных клиентов всё ещё не доказана.
3. **Новый фон — снова отложен по решению пользователя 3 октября:** новый кандидат Obsidian Horizon не принят. Сравнения и исходники сохранены в `outputs/design/wallpaper-refinement-20261003/`, но не предназначены для релиза. Фон по умолчанию не заменять; к обоям вернуться отдельно после оставшейся проверки интерфейса. Новых продуктовых функций сверх согласованного плана не добавлять.
4. **После решения выпускать (текущие обои остаются):** актуальные скриншоты магазинов, What's New RU/EN и ограничение JSON v2, номер версии, финальная сборка/валидация, отдельные папки/ZIP и согласованный push. Публикация — отдельное действие.

- Затем завершить общую приёмку Chrome/Firefox: реальные разрешения Firefox, сохранение/отмена настроек, emoji, свайпы, импорт/экспорт и сохранность данных. Учесть уже выполненные проверки; повторять их при изменениях или конкретных сомнениях.
- После приёмки подготовить согласованное состояние исходников и зафиксировать изменения в Git в рамках отдельного этапа. Этот порядок не является командой на push или публикацию прямо сейчас.
- В конце вернуться к качеству нового фона. После принятия итогового интерфейса и фона обновить продуктовые скриншоты, описание изменений RU/EN и подготовить релизные архивы, когда пользователь будет готов к выпуску.

История и детали предыдущих этапов ниже сохранены. Реализация Settings описана в `2026-09-30-ui-polish.md`.

## Цель и состав

Сделать повседневную навигацию удобнее, позволить отличать ссылки одного сервиса по собственным emoji и разобраться с доставкой обновлений — без потери сохранённых данных и изменения принятого внешнего вида.

В план входят три направления:

1. Проверка автообновлений и безопасное уведомление о готовой новой версии.
2. Переключение папок горизонтальными жестами тачпада.
3. Необязательный emoji вместо favicon у отдельного сайта.

Свайпы и emoji предназначены для Chrome и Firefox. Поведение обновлений проверяется отдельно для каждого браузера; одинаковый интерфейс не должен достигаться ценой ухудшения штатного обновления Firefox.

## Что сохраняем и чего не добавляем

- Принятые в 1.6 шапку, размеры и расположение карточек, прежний blur, отступы и три основные кнопки.
- Автофокус на URL при добавлении сайта, клавиатурную навигацию, действующие горячие клавиши и русский/английский интерфейс.
- Текущую архитектуру хранения: лёгкие данные в sync, пользовательский фон только в local; чанки, поколения и восстановление остаются внутри `storage-service.mjs`.
- Сайты, папки, порядок и настройки уже установивших расширение пользователей. Никаких сбросов или переустановки ради новых функций.
- Раздельные сборки Chrome и Firefox, Firefox-only настройки favicon и согласие на сетевые иконки.
- Без backend, OAuth, аналитики, загрузки чужого исполняемого кода, новых разрешений, большого emoji-каталога и отдельного редизайна Settings.
- Архивы и папки релиза 1.6 не перезаписывать. Новый релиз собирается отдельно после приёмки.

### 1.2. Рекомендуемый UX обновления

- Показывать небольшое сообщение только когда браузер действительно сообщил о готовом обновлении: «Доступно обновление» / “Update available”.
- Предлагаемые действия: «Обновить» / “Update” и «Позже» / “Later”. Без модального окна при каждом запуске, изменения высоты шапки и перекрытия основных кнопок.
- Не опрашивать магазин по таймеру и не проверять обновление при каждом рендере. Не создавать собственный сервер версий.
- Кнопка применяет готовое обновление только после проверки безопасности: нет незавершённых сохранений, импорта, загрузки фона или несохранённой формы ни в одной открытой вкладке расширения.
- Если безопасное применение подтвердить нельзя, не перезагружать расширение принудительно; дать понятное сообщение о необходимости завершить действия в других вкладках. Не запрашивать доступ ко всем вкладкам браузера ради этой проверки.
- Ошибка сохранения или недоступный API не должны приводить к перезагрузке, ложному сообщению об успехе или потере данных.
- В обычном браузерном preview, где API расширения нет, сообщение об обновлении скрыто.

Для Firefox нужно сначала проверить жизненный цикл: добавление обработчика `onUpdateAvailable` само может откладывать применение обновления. Рекомендуется сохранить штатное автообновление Firefox, если общий обработчик делает его хуже; Chrome-уведомление не переносить механически. Любой вариант с обработчиком должен иметь проверенный путь применения без бессрочного ожидания кнопки. [Документация Mozilla](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onUpdateAvailable).

**Критерий готовности этапа:** причина задержки проверена настолько, насколько позволяют доступные установки; ограничения записаны. Если уведомление реализуется, подтверждено, что оно помогает применить обновление и не теряет данные, не замедляет обычное обновление и не увеличивает разрешения. Код новой версии не может задним числом изменить поведение уже установленной 1.5.4.

## Этап 2. Свайпы между папками — первая пользовательская функция

22 сентября: на физическом тачпаде пользователь обнаружил пропуск повторного свайпа в обоих браузерах. Причина подтверждена записью событий: новый жест прерывал инерцию раньше ожидаемой кодом паузы. Исправление в общих исходниках и изолированных тестовых сборках; прошли 177 тестов и 38 браузерных проверок, включая повтор записанной последовательности, задержку сохранения и настоящее Chrome storage. После перезагрузки тестовых вкладок пользователь подтвердил работу повторных свайпов без тапов в Chrome и Firefox. [Результат, ограничения и ручная приёмка](../../folder-swipes-2026-09-22.md). Личные профили и релизные папки/архивы 1.6 не обновлялись; остальные ручные сценарии релизной приёмки отдельно не подтверждены.

### Рекомендуемое поведение

- Горизонтальный жест двумя пальцами над областью сайтов переключает соседнюю папку в видимом порядке, включая «Все» / “All”. На границах переключение останавливается, без перехода с последней папки на первую.
- Один намеренный жест — не более одного переключения. Остаточная инерция не пролистывает следующие папки; небольшой диагональный сдвиг при вертикальной прокрутке не считается свайпом.
- Над верхней строкой папок сохраняется нынешняя горизонтальная прокрутка самой строки. Жесты в контенте и прокрутка полосы папок не конкурируют.
- Не перехватывать вертикальную прокрутку, масштабирование, ввод текста, работу модальных окон или drag-and-drop.
- Выбранная папка остаётся видимой в строке. Шапка не становится выше; фон и карточки не получают тяжёлую анимацию. Учитывать настройку уменьшения движения.
- Начальное предложение для длинных списков: после успешного перехода показывать верх списка новой папки; не добавлять отдельное хранение позиции прокрутки для каждой папки. При ошибке сохранения оставлять прежнюю папку и позицию.
- Использовать существующий путь сохранения выбранной папки через актуальное состояние. Не писать в sync на каждое событие прокрутки и не возвращать старый снимок данных из давно открытой вкладки.

### Проверка

- [ ] Короткие и длинные жесты, инерция, диагональ, смена направления, повторный свайп после завершения предыдущего.
- [ ] «Все», пустые папки, первая/последняя папка, одна папка, много папок, переименование, удаление или изменение порядка в другой вкладке.
- [ ] Прокрутка строки папок, вертикальный scroll, масштабирование, клавиатура, открытая форма и перетаскивание.
- [ ] Ошибка storage и перезагрузка вкладки; отсутствие лишних записей.
- [ ] Реальный macOS-тачпад в Chrome и Firefox, включая системную настройку направления прокрутки и браузерный жест «назад/вперёд».

События `wheel` приходят не только от тачпада; план не предполагает надёжное распознавание устройства или точного количества пальцев. Реализация должна аккуратно распознавать горизонтальное намерение и корректно работать с другими источниками прокрутки. [Описание wheel в MDN](https://developer.mozilla.org/en-US/docs/Web/API/Element/wheel_event).

**Критерий готовности этапа:** соседняя папка выбирается предсказуемо, обычная прокрутка не ломается, один жест не даёт серию переходов. Одних искусственных wheel-событий недостаточно: без проверки настоящим тачпадом функцию нельзя объявлять полностью проверенной.

## Этап 3. Emoji вместо favicon

### Рекомендуемое поведение

- В существующей форме добавления/редактирования сайта — компактный выбор «Авто» / “Auto” или “Emoji” с предпросмотром.
- «Авто» остаётся по умолчанию. Все существующие сайты сохраняют свои favicon и буквенный fallback.
- Для emoji достаточно небольшого поля ввода/вставки одного символа, в том числе из системной панели emoji. Не добавлять большую библиотеку, отдельный экран или собственные загружаемые изображения.
- Можно заменить emoji или вернуть автоматическую иконку. Emoji относится только к конкретной ссылке: разные документы одного сервиса могут иметь разные значки.
- Размер и контейнер иконки остаются прежними; фокус при открытии формы остаётся на URL.
- Сайт с выбранным emoji не запрашивает favicon по сети. На других карточках действует прежняя политика Chrome/Firefox.
- Поддержать составные emoji — например, флаги, варианты тона кожи и последовательности с объединением символов. Несколько несвязанных emoji или обычный текст не принимать как один значок; объяснять ошибку рядом с полем.
- В данных хранить только небольшой Unicode-текст. Никаких картинок, base64 или favicon URL. Проверять ввод и выводить его как текст, не как HTML.

### Совместимость данных

- Новая версия читает существующие данные без emoji и не требует сброса настроек. Архитектуру storage не менять; новый необязательный атрибут проверить на совместимость отдельно.
- Если остальная запись корректна, повреждённое необязательное значение emoji не должно приводить к исчезновению всех сайтов: использовать автоматическую иконку для этой записи.
- Выбор сохраняется после редактирования, reload, перезапуска и синхронизации внутри одного семейства браузеров. Перенос между Chrome и Firefox — через JSON, не через общую синхронизацию.
- Проверить смешанные версии: старый клиент 1.6 при записи может не сохранить незнакомое поле. До выпуска явно определить и описать это ограничение; не обещать поддержку, которой нет.
- Текущий `backupVersion: 1` проверяет точный набор полей. Рекомендуемый вариант: новая версия читает старый v1 и новый v2; для нового экспорта с emoji использовать v2. Честно указать, что приложение 1.6 не сможет импортировать такой v2-файл. Отдельный режим «экспорт для старой версии» в этот релиз не добавлять.
- Пользовательский фон по-прежнему не входит в JSON-файл.

- [ ] Простые и составные emoji; ошибочный ввод; повреждённое значение; доступное имя ссылки и работа с клавиатуры.

## Предполагаемые участки кода

Это ориентир для последующих отдельных технических планов, не инструкция начинать изменения сейчас.

- Обновления: `extension-api.mjs`, отдельный небольшой модуль `update-service.mjs` при необходимости, подключение в `newtab.js`, локализованный UI в `newtab.html` и `styles.css`. Сначала проверить, достаточно ли обработчика во вкладке; не добавлять фоновые компоненты без подтверждённой необходимости.
- Свайпы: отдельный тестируемый модуль распознавания жеста, подключение в `newtab.js`, общая логика выбора папки; использовать существующий `handleFolderWheel` только для прокрутки строки папок.
- Emoji: `newtab.js`, `newtab-core.mjs`, форма в `newtab.html`, точечные стили, валидация и преобразование в `storage-service.mjs`, перенос в `backup-service.mjs`.
- Для всех изменений: `_locales/en/messages.json`, `_locales/ru/messages.json`, соответствующие unit tests и браузерные проверки.
- Для новых модулей: оба allowlist в `scripts/build-chrome.mjs` и `scripts/build-firefox.mjs`, build/isolation tests и осознанное обновление контрольного Chrome baseline. Firefox-специфичные решения остаются в overlay.

## Этап 4. Общая приёмка

- [ ] Каждый блок проходит собственные тесты до объединения с остальными. Перед изменением поведения добавить соответствующий регрессионный тест.
